Market onboarding applications — front-end handoff

Three standalone customer-facing onboarding applications — banking, healthcare and online gaming — each driving a published GBG Go journey through a thin backend proxy. This document defines the screens, the module chain and state machine per market, and the REST contract that both the Java and the TypeScript microservice must implement identically.

Scope note. The visual designs live in the companion prototype, Market Onboarding Journeys. That file is the reference for layout, copy and responsive behaviour; this document is the reference for structure and integration. Where the two disagree, the prototype wins on appearance and this document wins on data flow.

1. Architecture

Three separate front-end applications, deployed independently, sharing no runtime. Each talks to one backend microservice over REST. Two interchangeable implementations of that service exist — one Java, one TypeScript — serving the same contract, so a front end must not be able to tell which it is speaking to.

Request path
Browser — one of three apps. Renders screens, collects input, never holds a Go credential.
↓ REST over HTTPS, JSON
Onboarding service — Java or TypeScript. Holds the Go client credentials, mints and refreshes access tokens, forwards interaction traffic, keeps the session-to-instance mapping.
↓ GBG Go API v2
GBG Go — published journey per market, identified by resource ID.

Integration model: thin proxy. The front end drives Go's interaction loop. It starts a journey, fetches the current interaction to discover what data is outstanding, renders a form for it, submits, and repeats until the journey status leaves InProgress. The service adds authentication, request shaping and audit logging, and forwards. It does not model the journey itself.

The consequence worth stating plainly: screen order comes from the journey, not from the client. The step sequences in section 4 describe what a published journey currently produces — they are expected output, not a hard-coded route table. A journey edited in the Go builder changes the flow with no front-end release. Build the router off the interaction response.

Division of responsibility

Front end Microservice Go platform
Render fields from the interaction schema; client-side format validation; capture surfaces; progress and stage display; the result and record screens Go client credentials; token mint and refresh; session store; resource-ID selection per market; retry and idempotency; audit log; webhook receipt Journey definition; module execution; outcome and decision evaluation; branching; the authoritative journey state

Neither a Go access token nor a client secret may reach the browser under any circumstance.

2. REST contract

All paths are relative to a per-app base URL, supplied to the front end at build time as a single configuration value. JSON in and out, application/json except where noted. Both service implementations must match this contract to the field name.

Endpoint Purpose and shape
POST /v1/sessions Start a journey. Body carries an optional prefill object of known subject data. The service picks the resource ID from its own configuration — the client never names a journey. Returns sessionId, status, and the first interaction inline to save a round trip.
GET /v1/sessions/{id}/interaction The current interaction: interactionId, collects[], outstanding[], and the field schema for each domain element. This is the front end's routing signal — what it returns determines which screen renders.
POST /v1/sessions/{id}/interaction Submit collected data for the named interaction. Must be idempotent on interactionId — a double submit returns the same result rather than advancing twice. Returns the next interaction, or a terminal status.
GET /v1/sessions/{id}/state Journey status and, once reached, the decision. Polled while a processing screen is showing. Status values mirror Go: InProgress, PendingInput, Completed.
GET /v1/sessions/{id}/record The verification record shown on the final screen — journey name and version, reference, timestamps, elapsed time, per-module outcome and duration, deciding module where the outcome was not a straight pass. Composition is a policy decision; see section 6.
POST /v1/sessions/{id}/attachments Multipart upload for supplementary documents — proof of address, power of attorney. Returns an attachment reference to include in the next interaction submission.
GET /v1/config Per-app presentation configuration: brand name, accent colour, help contact, accepted document types, locale. Keeps brand values out of the front-end bundle so a deployment can be re-pointed without a rebuild.

Error envelope

One shape for every failure, from both implementations: an HTTP status, a stable machine code, a message safe to show a customer, an optional fields map for per-field validation errors, and a retryable boolean. The front end decides its treatment from code, never by parsing the message.

Code HTTP Front-end treatment
VALIDATION_FAILED422Field-level errors on the current screen, no navigation
SESSION_EXPIRED410Restart screen. Say what happened and offer to begin again.
INTERACTION_STALE409Re-fetch the interaction and re-render — the journey moved on
UPSTREAM_UNAVAILABLE503Retry with backoff behind the processing screen; surface after three attempts
RATE_LIMITED429Honour Retry-After; keep the customer on the current screen

Error copy follows the Go voice: say what happened and what to do next. Never blame the customer, never use the word "please".

3. Shared state machine

All three applications run the same seven states. Market differences live in the journey, not in the client.

State Behaviour and exit
idleIntro screen. Exit on start → POST /v1/sessions.
startingAwaiting session creation. On success store sessionId and move to collecting with the inline first interaction.
collectingRendering a screen from the interaction schema. Exit on submit → submitting. Back is a client-side move within an interaction only; it must not attempt to reverse a submitted one.
submittingPosting the interaction. Next interaction → collecting. Terminal status → decided. VALIDATION_FAILED → back to collecting with field errors.
processingNo outstanding data, no decision yet. Poll /state. Show module progress. Cap the wait, then fall through to a holding screen rather than spinning indefinitely.
decidedResult screen, branching on decision: pass, refer or decline. Fetch /record for the verification record panel.
failedUnrecoverable transport or session error. Offer a restart. Distinct from a declined decision, which is a successful journey with a negative outcome.

A referral is not a failure state. It is a decision that leaves the journey open, sometimes with a further interaction — the banking proof-of-address flow returns to collecting after a referral.

5. Mock mode

Each front end must run with no backend present, so the applications can be demonstrated and tested before either service is finished. One configuration flag switches the transport layer between live REST and a canned fixture set; nothing above the transport layer knows which is active.

Fixtures should cover every designed outcome, not just the happy path: banking straight-through and referral, healthcare patient and carer, gaming instant pass, step-up and jurisdiction block. Add fixtures for the error envelope too — a stale interaction, an expired session and an upstream outage each need a demonstrable screen. The same fixture set doubles as the contract test both service implementations run against.

6. Open decisions

Six items that need an owner before build. Each changes the contract or the screens.

Front-end authentication to the service
Undecided. Recommendation: a first-party HTTP-only session cookie set by the service on POST /v1/sessions, scoped to the session and short-lived. It keeps the session identifier out of URLs and browser history, needs no identity provider for an anonymous onboarding flow, and works the same in both implementations. If a journey must be resumable across devices, a signed resume link is the alternative — that is a different threat model and needs a decision of its own.
Prefill versus non-prefill
If an app already holds name, date of birth and address, sending them at start and removing those domain elements from the interaction group deletes the Details screen entirely. Gaming and healthcare are the likely candidates. Decide per app, because it changes the screen count in section 4.
Capture SDK integration
Document and selfie surfaces are placeholders in the current designs. Real capture needs GBG's Web SDK mounted in the page, and it owns its own camera UI — so the surrounding chrome is ours and the viewfinder is not. Confirm which SDK version, and re-review those two screens once it is in.
Composition of the verification record
The record panel on the final screen is a design proposal, not an existing payload. Instance reference, timestamps, elapsed time, module outcomes and the decision all exist in Go. What a customer should see — particularly the deciding module on a referral or decline — is a compliance judgement. Settle it before building /record, since it defines that endpoint.
Decision delivery to your own systems
The browser polling /state is for showing progress, not for provisioning. Account creation should hang off a webhook or a server-side state check, so a customer closing the tab does not lose a completed verification.
Journey versioning
Pinning @latest means a journey edit reaches production without a release — convenient, and a change-control problem in regulated markets. A fixed resource ID per environment, promoted deliberately, is the safer default for banking. Decide per market.

7. Not yet designed

Known gaps in the current screen set, in rough order of how likely a customer is to hit them.

  • Session resume — returning to a part-finished journey, on the same device or another
  • Document capture retry, and the copy for a rejected or unreadable image
  • Camera and file permission refusal, and the fallback route when a customer has no camera
  • Timeout on a processing screen that never resolves
  • Accessibility pass — the designs have not been checked against a keyboard-only or screen-reader run
  • Localisation — copy is British English only; Go supports interaction translations, which changes field labels and layout width
